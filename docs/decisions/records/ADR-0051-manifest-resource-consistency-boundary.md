# ADR-0051: Определить границу согласованности manifest resources

## Статус

Accepted

---

## Контекст

На момент принятия решения `ManifestResources` объединяет ресурсы из `Manifest.files`, `Manifest.libraries` и
`Manifest.assetsIndex` в общий список `ResourceEntry`

Selected native artifacts участвуют в этом списке через compatibility projection в `Manifest.libraries`

Verification/download lifecycle использует общий resource-level contract независимо от исходного типа manifest metadata

Каждый ресурс содержит

- `path`
- `sha256`
- `size`
- `url`

Разные записи могут указывать на один локальный файл и содержать противоречивую физическую метадату

Один локальный файл не может одновременно соответствовать разным ожидаемым значениям `sha256` или `size`

Последовательная загрузка таких записей может перезаписывать один файл и завершаться ошибкой повторной verification

Сравнение исходных строк `path` недостаточно

Разные относительные пути могут разрешаться в одно локальное назначение после нормализации

Поэтому общий набор ресурсов должен получать проверку согласованности до выполнения resource verification и загрузки

---

## Решение

Подготовка согласованного набора ресурсов должна принадлежать `launcher-core`

Для этой ответственности вводится общий planning-компонент `ResourceSetPlanner`

Входными данными являются список `ResourceEntry` и игровая директория

Локальные назначения должны определяться через существующий `ResourcePathResolver`

`ResourceSetPlanner` не должен выполнять чтение файлов, хеширование, создание директорий или загрузку ресурсов

Результатом подготовки должен быть immutable `ResourceSetPlan`

План должен содержать исходную метадату выбранных ресурсов и их разрешенные локальные пути

Ресурсы имеют одинаковое локальное назначение, если их разрешенные нормализованные `Path` равны согласно правилам
используемого filesystem provider

Исходная строка `ResourceEntry.path` не является достаточной идентичностью локального назначения

Записи с одинаковым назначением совместимы, если их значения `sha256`, `size` и `url` равны

Совместимые записи должны объединиться с сохранением первой записи и исходного порядка уникальных назначений

Объединение применяется только к подготовленному resource-level плану и не изменяет исходные manifest-specific коллекции

Различие `sha256`, `size` или `url` при одинаковом назначении является конфликтом

Конфликт должен завершать подготовку всего набора ошибкой

Диагностика конфликта должна позволять определить локальное назначение и исходные записи

Частично подготовленный план не должен передаваться на обработку

Verification и download должны использовать общий механизм подготовки ресурсов

Verification должна подготавливать полный набор из `ManifestResources` до начала проверки файлов

Download должна подготавливать полный набор из `DownloadPlan.resources` до начала загрузки независимо от происхождения
`DownloadPlan`

Оба flow должны использовать локальные пути из подготовленного плана

Граница выглядит так

```text
Manifest
    -> ManifestResources
        -> ResourceSetPlanner
            -> ResourceSetPlan
                -> resource verification

DownloadPlan.resources
    -> ResourceSetPlanner
        -> ResourceSetPlan
            -> resource download
```

`ManifestResources` остается projection layer и не получает ответственность за локальные назначения

`ResourceEntry` остается generic recoverable resource contract

`FileEntry`, `LibraryEntry` и `AssetEntry` сохраняют собственную семантику

`launcher-app` отвечает за связывание planning-компонента с verification и download adapters

`LauncherEngine` не получает новую operation или ответственность за сравнение ресурсов

---

## Рассмотренные варианты

### Сравнивать исходные строки `path`

Вариант отклонен

Разные относительные пути могут разрешаться в одно локальное назначение

Сравнение строк не обнаруживает такие совпадения

### Отклонять любые повторные назначения

Вариант отклонен

Разные manifest-specific коллекции могут описывать один ресурс с одинаковой метадатой

Такие записи не являются противоречием и могут быть объединены без выбора приоритета между источниками

### Выбирать первую или последнюю конфликтующую запись

Вариант отклонен

Порядок ресурсов не должен определять, какая противоречивая метадата будет использована

Такой подход скрывает конфликт и делает результат зависимым от порядка manifest-specific коллекций

### Проверять согласованность независимо внутри каждого adapter

Вариант отклонен

Verification и download должны использовать одинаковые правила идентичности и совместимости ресурсов

---

## Последствия

Verification/download flow получает общую границу подготовки согласованного набора ресурсов

Противоречивые назначения должны обнаруживаться до начала проверки файлов или загрузки

Совместимые повторные записи не должны приводить к повторной обработке одного назначения внутри подготовленного плана

Manifest domain model остается независимой от игровой директории и локальной файловой системы

Существующие наборы ресурсов без совпадающих назначений должны сохранять исходный порядок обработки

Trade-off решения в том, что подготовка требует разрешения всех путей и хранения промежуточного плана до начала обработки
ресурсов

Разные URL для одного назначения считаются конфликтом даже при одинаковых `sha256` и `size`

Это ограничение сохраняет однозначный источник загрузки до появления отдельной mirror selection policy

Проверка основана на нормализованных путях и не гарантирует обнаружение всех способов обращения к одному физическому файлу

Если позже потребуется учитывать physical file identity или выбирать между несколькими источниками загрузки, эти границы
должны быть оформлены отдельными решениями

---

## Не входит в решение

- Изменение manifest JSON contract
- Новая launcher operation
- Изменение operation sequence
- Выбор приоритета между конфликтующими ресурсами
- Mirror selection или URL fallback policy
- Нормализация URL
- Определение physical file identity через real path, symbolic links или hard links
- Проверка конфликтов между назначением файла и родительской директорией другого ресурса
- Транзакционная загрузка и rollback
- Защита от изменений файловой системы между подготовкой и обработкой ресурсов
- Parallel downloads
- Retry policy
- Resource cache versioning
