# ADR-0069: Определить границу принятия управляемого манифеста

## Статус

Accepted

---

## Контекст

На момент принятия решения [ADR-0066](ADR-0066-publisher-managed-manifest-source-boundary.md), [ADR-0067](ADR-0067-startup-manifest-source-selection-boundary.md) и [ADR-0068](ADR-0068-bundled-manifest-uri-source-boundary.md)
определяют управляемый источник манифеста, порядок его выбора и поставку manifest URI в составе приложения

После выбора источника `LauncherConfiguration` сохраняет URI, но не сохраняет способ его выбора

`HttpManifestService` загружает и преобразует ответ в `ManifestLoadResult` без отдельной границы принятия манифеста

Структурная проверка URI и последующая проверка файлов по размеру и SHA-256 не подтверждают подлинность самого манифеста:
ожидаемые значения для файлов поступают из его содержимого

Необходимо отделить выбор управляемого источника от принятия полученного манифеста, не перенося политику источника в
`launcher-core`

---

## Решение

`launcher-app` сохраняет сведения о выбранном режиме источника до сборки загрузки манифеста

Режим управляемого источника фиксируется результатом выбора источника при startup, а не выводится из значения URI или наличия
упакованного ресурса

Для управляемого источника загруженный ответ проходит отдельную проверку принятия до возврата `ManifestLoadResult` в launcher
lifecycle

`launcher-app` выбирает необходимую политику по режиму источника, а граница загрузки манифеста применяет ее до передачи результата
в `launcher-core`

`launcher-core` получает только результат успешной загрузки и не определяет происхождение источника или политику его принятия

Явный manifest URI и `--local-config` остаются техническими способами запуска и не получают статус доверенного управляемого
источника

Ошибка принятия управляемого манифеста завершает загрузку манифеста ошибкой без автоматического перехода к техническому
источнику

Для такой ошибки используется существующий failure flow загрузки манифеста без нового состояния launcher lifecycle

Выбор конкретного способа подтверждения подлинности управляемого ответа требует отдельного решения

Наличие границы принятия само по себе не делает текущий сетевой ответ доверенным

---

## Рассмотренные варианты

### Определить управляемый источник по совпадению URI

Вариант отклонен

Один и тот же URI может быть передан явно в техническом режиме, поэтому значение URI не сохраняет происхождение выбора

### Проверять происхождение манифеста в `launcher-core`

Вариант отклонен

`launcher-core` оркестрирует загрузку и использует ее результат, но не отвечает за выбор источника и сетевую политику доверия

### Сразу зафиксировать способ подтверждения подлинности

Вариант отложен

Граница принятия необходима до поставки действительного URI управляемого источника, а конкретный механизм проверки подлинности
и правила управления его параметрами требуют отдельного решения

---

## Последствия

Выбранный режим источника потребуется сохранять за пределами `LauncherConfigurationResolver` до application assembly

Загрузка управляемого манифеста не сможет вернуть `ManifestLoadResult` при неуспешной проверке принятия

Тесты должны различать управляемый и явно выбранные технические источники, а также подтверждать отсутствие fallback при
ошибке принятия

Дополнительная передача сведений об источнике усложняет startup assembly, но не позволяет принять технический источник за
управляемый

До выбора и реализации конкретной проверки подлинности это решение не завершает подготовку обычного пользовательского запуска
с внешним манифестом

---

## Не входит в решение

- Конкретный manifest URI и способ размещения манифеста
- Подпись манифеста, управление ключами и иной конкретный механизм подтверждения подлинности
- Политика допустимых источников ресурсов из манифеста
- Проверка локальных файлов на символические ссылки и изменения между проверкой и записью
- Retry, fallback и изменения launcher lifecycle
- Изменение технических способов запуска
