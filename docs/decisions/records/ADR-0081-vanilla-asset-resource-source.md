# ADR-0081: Определить источник vanilla assets для управляемого манифеста

## Статус

Accepted

---

## Контекст

На момент принятия решения [ADR-0080](ADR-0080-vanilla-asset-preparation-boundary.md) относит проверку vanilla asset index
и полного набора его объектов к стороне подготовки управляемого манифеста

`launcher-preparer` уже получает проверенные метаданные индекса и объектов, но источник объектов предоставляет только поток
байтов без URI будущего ресурса

`AssetIndexMetadata` и `AssetEntry` требуют URI, по которым launcher сможет получить объявленные байты

[ADR-0073](ADR-0073-managed-manifest-resource-uri-boundary.md) требует для ресурсов управляемого манифеста абсолютные
HTTPS URI и запрещает перенаправление при загрузке

Необходимо определить связь между проверяемыми байтами и URI манифеста, не вводя собственное размещение ресурсов без
подтвержденной необходимости

---

## Решение

Для первого подтвержденного vanilla-сценария сторона подготовки использует URI выбранного HTTPS-источника как URI ресурсов
управляемого манифеста

Источник каждого ресурса связывает URI и доступ к его байтам: проверка файла индекса и объектов выполняется по тем URI,
которые затем указываются в `AssetIndexMetadata` и `AssetEntry`

Подстановка другого URI после проверки байтов не допускается

URI должен соответствовать политике ресурсов управляемого манифеста и предоставлять байты без HTTP-перенаправления

Недоступность ресурса, перенаправление или несовпадение его байтов с ожидаемыми метаданными останавливают подготовку полного
набора ресурсов

Манифест фиксирует вычисленные при подготовке SHA-256 и размеры ресурсов согласно [ADR-0080](ADR-0080-vanilla-asset-preparation-boundary.md)

Сторона подготовки не копирует объекты в собственное хранилище для этого сценария

Launcher не получает новый способ интерпретации asset index и продолжает проверять загруженные ресурсы по метаданным
подписанного манифеста

---

## Рассмотренные варианты

### Размещать проверенные байты в собственном хранилище

Вариант отложен

Он позволил бы контролировать доступность ресурсов, но потребовал бы отдельной границы размещения, проверки опубликованных
байтов и сопровождения хранилища до появления подтвержденной потребности

К варианту следует вернуться, если выбранный источник не обеспечивает доступность ресурсов по URI, допустимым для управляемого
манифеста

### Проверять байты из одного источника, а в манифест записывать независимый URI

Вариант отклонен

Такая подготовка не подтверждает, что URI манифеста предоставляет ресурс, байты которого были проверены

---

## Последствия

Для первого vanilla-сценария не требуется собственное хранилище asset objects

Граница источника должна предоставлять стороне подготовки и URI, и байты одного разрешенного ресурса

Подготовка зависит от доступности выбранного HTTPS-источника и от возможности получить ресурс без перенаправления

Проверка при подготовке не гарантирует неизменность или будущую доступность внешнего источника

Если по опубликованному URI позже будут возвращены другие байты, launcher отклонит их при проверке размера и SHA-256

Недоступный ресурс также не сможет быть восстановлен

Решение не меняет launcher lifecycle и не устанавливает доверие к происхождению исходных Minecraft metadata

---

## Не входит в решение

- Выбор конкретного host и действительных URI
- Собственное размещение, копирование и повторное использование байтов ресурсов
- Cache policy, retry, resume и cancellation
- Изменение локальных путей `AssetIndexMetadata` и `AssetEntry`
- Подготовка остальных частей vanilla-манифеста
- Host allowlist и ограничение сетевых адресов
