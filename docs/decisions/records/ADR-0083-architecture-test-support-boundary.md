# ADR-0083: Определить границу общей поддержки архитектурных тестов

## Статус

Accepted

> Примечание: решение реализовано в итерации
> `refactor(test): share java source import parsing`
>
> Граница файловой поддержки уточнена в [ADR-0084](ADR-0084-architecture-source-inspection-boundary.md)

---

## Контекст

На момент принятия решения `CoreImportBoundaryCheck` и `UiImportBoundaryCheck` разбирают Java source для проверки
модульных зависимостей

Проверки используют разные правила допустимости imports, но повторяют получение Java compiler, parsing и обработку
синтаксических ошибок

Для закрепления границы между launcher-app и presentation-specific реализациями требуется тот же механизм разбора

Общая техническая ответственность уже подтверждена несколькими потребителями, но не относится к runtime лаунчера

Необходимо определить место общего parsing без объединения политик разных модулей и без добавления production-зависимостей

---

## Решение

Общая поддержка архитектурных тестов принадлежит инструментальному модулю `launcher-architecture-test-support`

Модуль располагается в `tools/architecture-test-support` и не зависит от production-модулей проекта

Потребители подключают его только через `testImplementation`

Включение этого модуля в runtime classpath приложения не допускается

Первым общим компонентом является `JavaSourceImportParser`

Он получает Java source как строку и возвращает упорядоченный неизменяемый список `JavaSourceImport`

Описание import сохраняет имя импортируемого элемента и различие обычного и static import

Разбор выполняется без компиляции исходника и разрешения импортируемых типов

Синтаксически некорректный source отклоняется, а ошибка parsing не преобразуется в пустой успешный результат

Чтение файлов, выбор проверяемых исходников и правила допустимости imports остаются у потребителей

`CoreImportBoundaryCheck` сохраняет правила launcher-core

`UiImportBoundaryCheck` сохраняет существующие allowlists launcher-ui без автоматического разрешения static members
или вложенных типов

Инструментальный модуль не определяет допустимые зависимости production-модулей и не получает ответственность
за launcher lifecycle

---

## Рассмотренные варианты

### Разместить общую поддержку в launcher-common

Вариант отклонён

Подтверждённый cross-module сценарий допускается политикой reserved modules

Размещение в test fixtures позволило бы сохранить тестовый scope без нового Gradle project

Для данного сценария выбран отдельный инструментальный модуль, чтобы не связывать поддержку architecture checks
с reserved shared primitives boundary

### Использовать test fixtures одного из потребителей

Вариант отклонён

Общий синтаксический разбор не является ответственностью launcher-core или launcher-ui

Размещение у одного из потребителей связывает общую техническую поддержку с модулем, чьи правила она должна
помогать проверять

---

## Последствия

Общий механизм parsing получает одно место реализации и проверки

Политики модульных зависимостей остаются независимыми и не переносятся в общий parser

Существующие результаты architecture checks должны сохраняться после выделения общей части

Изменения parser могут затронуть нескольких потребителей и требуют подтверждения существующими regression tests

В Gradle build появляется дополнительный инструментальный модуль и публичный API, который необходимо сопровождать

Тестовый scope зависимости должен сохраняться при дальнейшем развитии потребителей

---

## Не входит в решение

- Изменение правил модульных зависимостей и существующих allowlists
- Объединение с buildSrc
- Полный анализ Java type references и графа Gradle dependencies
- Перенос других fixtures и создание универсального test framework
- Добавление shared primitives в launcher-common
- Изменение launcher lifecycle и production wiring
