# ADR-0084: Определить границу файловой поддержки архитектурных проверок

## Статус

Accepted

> Примечание: решение реализовано в итерации
> `refactor(test): share architecture source inspection`

---

## Контекст

На момент принятия решения architecture checks для launcher-core, launcher-ui и launcher-app используют общий
`JavaSourceImportParser` согласно [ADR-0083](ADR-0083-architecture-test-support-boundary.md)

Потребители повторяют поиск корня проекта, обход Java source, чтение файлов и формирование диагностик

Правила допустимости imports различаются и остаются ответственностью проверяемых модулей

ADR-0083 оставляет файловую работу у потребителей

Необходимо определить границу общей файловой поддержки, сохранив независимость модульных правил и результаты существующих
сценариев

---

## Решение

Общая файловая поддержка import-based architecture checks принадлежит инструментальному модулю
`launcher-architecture-test-support`

Она включает поиск корня Gradle project от явно переданной директории, чтение отдельного исходного файла и обход
Java-файлов в переданной директории

Выбор проверяемого модуля и директории исходников остается у потребителя

Общая поддержка не содержит имен production-модулей, запрещенных namespaces или списков разрешенных imports

Потребитель передает проверку исходного текста, возвращающую запрещенные import declarations

`CoreImportBoundaryCheck`, `UiImportBoundaryCheck` и `AppImportBoundaryCheck` сохраняют собственные правила

Разбор Java source остается ответственностью `JavaSourceImportParser`, который не получает файлового доступа

Результатом файловой проверки является неизменяемый список строковых диагностик с путем исходного файла

Формат диагностик и порядок запрещенных imports внутри файла сохраняются

Ошибка чтения или parsing отдельного файла формирует диагностику невозможности проверки и не преобразуется в пустой
успешный результат

Отсутствие корня проекта или ошибка обхода директории завершают проверку ошибкой

Открытые файловые ресурсы закрываются до возврата результата

Проверка размещения известных concrete adapters в launcher-core остается у потребителя и не включается в общий механизм
проверки imports

Решение изменяет границу ADR-0083 только в части общей файловой поддержки

Независимость инструментального модуля от production-модулей и подключение только через `testImplementation` сохраняются

---

## Рассмотренные варианты

### Ввести общий базовый класс архитектурных тестов

Вариант отклонён

Общей является файловая механика, а не структура всех тестовых сценариев

Композиция позволяет сохранить самостоятельные проверки модулей без общей иерархии и зависимости файловой поддержки
от JUnit lifecycle

### Перенести модульные правила в общий механизм

Вариант отклонён

Правила launcher-core, launcher-ui и launcher-app имеют разные причины изменения

Общая поддержка выполняет переданную проверку, но не определяет допустимые зависимости модулей

---

## Последствия

Файловая механика получает одно место реализации и самостоятельное regression coverage

Исправления чтения исходников и формирования диагностик не требуют повторения в каждом потребителе

Модульные правила и проверки их подключения остаются локальными

Изменения общей поддержки могут затронуть несколько модулей и требуют подтверждения существующими regression tests

Публичный API инструментального модуля расширяется и требует сопровождения

Выделение общей части не должно уменьшать проверяемый набор исходников или скрывать ошибки проверки

---

## Не входит в решение

- Изменение модульных правил и существующих allowlists
- Перенос проверки размещения concrete adapters
- Автоматическое обнаружение всех модулей проекта
- Создание общей иерархии тестов или универсального test framework
- Перенос остальных fixtures и массовая переработка тестовых сценариев
- Полный анализ Java type references и графа Gradle dependencies
- Изменение production code, launcher lifecycle или wiring
