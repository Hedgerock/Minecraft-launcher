# Ретроспектива: стабилизация runtime-жизненного цикла запуска

## Контекст

Данная итерация расширила launcher от архитектурного каркаса к полноценному runtime-сценарию
запуска

До начала этапа `LauncherEngine` уже использовал `OperationManager`, но жизненный цикл еще не покрывал
полный путь от загрузки манифеста до запуска игрового процесса

Целью этапа было постепенно довести основной сценарий запуска до состояния, где каждый шаг выражен
отдельной операцией, имеет понятный результат, покрыт тестами и отражен в документации

## Что было сделано

- Добавлена проверка файлов после загрузки `Manifest`
- Добавлено построение `VerificationPlan`
- Добавлен `DownloadPlan`
- Добавлен этап `BUILD_DOWNLOAD_PLAN`
- Добавлен этап`DOWNLOAD_FILES`
- Добавлена повторная проверка файлов после загрузки
- Добавлена подготовка директорий перед запуском игры
- Добавлен `GameLaunchPlan`
- Добавлен этап `BUILD_GAME_LAUNCH_PLAN`
- Добавлен запуск игрового процесса через `GameService`
- Добавлена реализация `Sha256HashService`
- Добавлена реализация запуска процесса через `ProcessBuilder`
- Усилена валидация моделей `Manifest`, `FileEntry`, `LaunchInfo`, `LoaderInfo`
- Усилена валидация планов `VerificationPlan`, `DownloadPlan`, `GameLaunchPlan`
- Обновлена документация жизненного цикла, модульных границ и потоков выполнения
- Восстановлен Gradle Wrapper для воспроизводимого запуска сборки

## Что подтвердилось

Архитектурное разделение `launcher-core` и адаптеров оказалось устойчивым

`launcher-core` хорошо подходит для владения orchestration-логикой, состояниями, операциями и
планами выполнения

Конкретные детали загрузки, проверки файлов, хеширования и запуска процесса лучше остаются за пределами core и
подключаются через композиционный корень

Модель `OperationManager -> LaunchOperation -> LauncherTask` позволила добавлять новые этапы без переписывания
всего жизненного цикла

## Что было улучшено архитектурно

`LauncherEngine` стал ближе к роли координатора жизненного цикла

Он принимает решения о следующем шаге на основании результатов операций, но не выполняет детали загрузки, проверка
файлов или запуска процесса самостоятельно

`GameLaunchPlan` отделил построение входных данных запуска от самого запуска процесса

`DownloadPlan` отделил решение о том, какие файлы нужно восстановить, от механизма их загрузки

Валидация моделей была перенесена ближе к месту создания данных, что уменьшает вероятность некорректного состояния в
runtime flow

## Что осталось отложенным

- Реальный парсинг JSON-манифеста
- Полная модель classpath
- Выбор Java executable
- Аргументы авторизации и пользовательской сессии
- Более богатая модель жизненного цикла запущенного процесса
- Обязательность `Manifest.loader` на уровне общего контракта
- Более строгие архитектурные тесты для всех модульных границ
- Очистка исторических ADR/RFC от смешения языков

## Технический долг

Технический долг остается контролируемым

Критический долг по воспроизводимости сборки был закрыт восстановлением Gradle Wrapper

Оставшийся долг в основном относится к исторической документации, деталям production-ready адаптеров
и будущему расширению launch-metadata

Также остается вопрос постепенного выноса исторических инфраструктурных реализаций из `launcher-core`, если они больше
не соответствуют текущим модульным границам

## Главный вывод

Milestone подтвердил выбранный подход: launcher можно развивать небольшими инженерными итерациями, сохраняя
архитектурные границы и не вводя преждевременные абстракции

Основной runtime lifecycle теперь выражен явно

```text
LOAD_MANIFEST
    -> VERIFY_FILES
    -> BUILD_DOWNLOAD_PLAN
    -> DOWNLOAD_FILES
    -> VERIFY_FILES
    -> PREPARE_DIRECTORIES
    -> BUILD_GAME_LAUNCH_PLAN
    -> LAUNCH_GAME
    -> RUNNING
```
При ошибке на любом этапе launcher переходит в `FAILED`
