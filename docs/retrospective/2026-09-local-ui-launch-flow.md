# Ретроспектива: local UI launch flow

## Контекст

Данный milestone развил локальный JavaFX launch flow после `v0.8.0-presentation-launch-boundary`

До начала этапа UI мог передать запрос запуска и показать его исход, но обычный startup еще не имел локального источника
manifest URI и контролируемого представления ошибок исходной конфигурации

Целью этапа было сделать локальный сценарий запуска воспроизводимым, сохранив границу между startup-конфигурацией, выполнением
launch request и его представлением

---

## Что было сделано

- Добавлены локальная диагностика неожиданных сбоев presentation launch flow и передача этапов принятого запроса в UI
- Подключены manifest URI из `keystone.properties` и платформенные пользовательские каталоги
- Для локального и явно заданного manifest URI введены единые требования проверки до создания `LauncherConfiguration`
- Ожидаемые ошибки startup-конфигурации отображаются безопасно и не превращаются в неуспешный `LaunchResult`
- Для ошибки локального источника добавлена повторная подготовка конфигурации после внешнего исправления
  `keystone.properties`
- Добавлена пользовательская подсказка для исправления локальной конфигурации без отображения URI или пути к файлу
- Opt-in JavaFX smoke-тестом подтверждены запуск через явный URI локального HTTP-сервера, отображение этапов и старт игрового
  процесса

---

## Что подтвердилось

Ошибка startup-конфигурации возникает до принятия launch request и не должна представляться как результат launcher lifecycle

Повторное чтение исправленного `keystone.properties` не является retry policy для повторного запуска игры

Явно заданный manifest URI имеет приоритет над локальным источником и не использует его как fallback

Presentation layer может показывать этапы принятого запроса через application boundary без прямой подписки на внутренние
события `launcher-core`

Технические сообщения исключений, локальные пути и manifest URI не должны попадать в пользовательский статус напрямую

---

## Что было улучшено архитектурно

`launcher-app` отвечает за подготовку startup-конфигурации, проверку manifest URI и доставку этапов принятого launch request

`launcher-ui` отвечает за startup state, доступность действий и безопасное представление ошибок и этапов

`launcher-core` не получил зависимость от локального конфигурационного файла или JavaFX

Граница между ошибкой подготовки приложения и исходом принятого запроса стала явной

---

## Что осталось отложенным

- Создание и редактирование `keystone.properties` в UI
- Доверие к манифесту и целостность локальных ресурсов
- Retry policy для повторного launch request и recovery actions после launch failure
- Cancel behavior и потоковый progress отдельных операций
- Отслеживание lifecycle запущенной игры
- Локализация и расширение пользовательского flow настройки

---

## Технический долг

Текущее покрытие подтверждает локальный UI launch flow через явно заданный manifest URI

Opt-in JavaFX smoke-тест пока не воспроизводит чтение `keystone.properties` и действие Retry

Их поведение проверяется более узкими тестами

Это ограничение тестового среза не меняет установленную границу startup-конфигурации, но к сквозному сценарию следует
вернуться при дальнейшем развитии локальной настройки

---

## Главный вывод

Milestone довел минимальный локальный UI launch flow до воспроизводимого запуска и контролируемой обработки ошибок
startup-конфигурации без изменения launcher lifecycle

Полученный результат остается инженерным прототипом: наличие локального источника манифеста не означает, что уже решены
вопросы доверия к нему, полноценной настройки приложения и восстановления после ошибок запуска

Следующее направление стоит выбрать после подготовки релиза и отдельной ревизии
