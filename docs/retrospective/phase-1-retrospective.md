# Phase 1 Retrospective

## Цель

Зафиксировать основные инженерные выводы, сделанные в процессе построения архитектурного
фундамента Launcher

Документ предназначен для сохранения принятых практик перед переходом ко второй фазе
разработки

## Результаты

- Архитектура проектировалась эволюционно, без преждевременного усложнения
- Большинство решений сначала фиксировалось в RFC и ADR, а затем переходило в реализацию
- Документация развивалась одновременно с архитектурой, а не после написания кода
- Каждый компонент получал четко определенную зону ответственности
- Были сформированы инварианты, используемы при принятии новых решений
- Проведен полный Architecture Review перед завершением первой фазы

## Практики, которые необходимо сохранить

- Сначала проектировать, затем реализовывать
- Не создавать новые абстракции без реальной необходимости
- Любое архитектурное решение должно иметь владельца
- Проверять решения через инварианты, а не через личные предпочтения
- Использовать RFC для изменения поведения системы
- Использования ADR для фиксации архитектурных решений
- Выполнять Architecture Review перед завершением крупных этапов

## Сложные моменты

- Правильно определить границы ответственности компонентов
- Не создавать лишние уровни абстракции
- Научиться отличать перспективное масштабирование от преждевременного
- Научиться принимать решения через архитектурные принципы

## Изменения

На раннем этапе большинство решений принималось интуитивно

К завершению первой фазы основным источником принятия решений стали:

- RFC
- ADR
- Инварианты
- Документация
- Architecture Review

## Переход ко второй фазе

Во вторую фазу переносятся следующие инженерные практики

- Ведение CHANGELOG
- Ведение Architecture Decision Records
- Ведение RFC
- Поддержание Documentation Backlog
- Проведение Architecture Review
- Развитие документации одновременно с развитием архитектуры

## Основная Phase 2

Использовать сформированный архитектурный фундамент для построения потокобезопасной многопоточной
системы Launcher без нарушения существующих вариантов

## Главный вывод

Главной ценностью первой фазы стала не документация и не количество реализованных компонентов

Главным результатом стало формирование инженерного процесса, позволяющего принимать
архитектурные решения последовательно, аргументированно и без необходимости возвращаться
к уже принятым решениям

## Чего следует избегать

- Не внедрять многопоточность до появления реальной необходимости
- Не заменять простые решения сложными без объективной причины
- Не нарушать существующие инварианты ради локальной оптимизации
- Не изменять архитектурные границы без RFC или ADR
- Не переносить бизнес-логику в инфраструктурные компоненты
