# Правила написания ADR

## Назначение

ADR фиксирует принятое архитектурное решение и объясняет, почему оно было принято

ADR не является планом реализации, отчетом о проделанной работе или подробной технической спецификацией

---

## Структура ADR

Каждый новый ADR должен использовать единую структуру

```text
# ADR-XXXX: Краткое название решения

## Статус

Accepted

---

## Контекст

...

---

## Решение

...

---

## Последствия

...

---

## Не входит в решение

...

---

## Связанные решения

...
```
---

## Контекст

Раздел `Контекст` описывает состояние проекта до принятия решения

В этом разделе нужно объяснить

- Какая проблема появилась
- Какие границы ответственности затрагиваются
- Почему текущее состояние больше недостаточно
- Какие уже существующие решения влияют на новый выбор

Раздел не должен описывать пошаговый план реализации

---

## Решение

Раздел `Решение` фиксирует выбранный подход

В этом разделе нужно описать

- Какой компонент получает новую ответственность
- Какой компонент не получает новую ответственность
- Как выглядит новая граница
- Какие модели, операции или contracts становятся source-of-truth

Если решение затрагивает поток данных, допускается использовать компактную `text`-схему

---

## Последствия

Раздел `Полсдествия` описывает влияние решения на проект

В этом разделе нужно указать

- Какие границы стали яснее
- Какие компоненты должны измениться в будущей реализации
- Какие компромиссы появились
- Какие старые сценарии должны остаться совместимыми

---

## Не входит в решение

Раздел `Не входит в решение` защищает ADR от расширения scope

В этом разделе нужно явно перечислить связанные, но отложенные темы

Например

- Future behavior
- Adapter implementation details
- Runtime-specific extensions
- Cleanup policies
- Backward incompatible changes
- ...

---

## Связанные решения

Раздел `Связанные решения` содержит ссылки на ADR, которые влияют на новое решение или получают
развитие после него

Ссылки должны использовать относительный путь внутри `docs/decisions`

---

## Стиль

ADR пишется в декларативном стиле

Предпочтительно использовать короткие абзацы без лишнего повествования

Технические термины допускаются, если они уже используются в проекте

Документ должен соблюдать правило единого языка документации

---

## Примечание после реализации

Если решение уже реализовано, после статуса можно добавить примечание

```text
> Примечание: решение реализовано в итерации `commit message`
```

Если решение реализовано несколькими итерациями

```text
> Примечание: решение реализовано в итерациях
> `first commit message`
> `second commit message`
> `n commit message`
```

Примечание не заменяет раздел `Последствия`

---

## Чего избегать

В ADR не стоит добавлять

- Большие фрагменты production code
- Подробные инструкции по реализации
- Несогласованные будущие возможности
- Дублирование уже существующих ADR
- Смешение языков внутри документа
- Формулировки, которые обещают реализацию до ее появления
