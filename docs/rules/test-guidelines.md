# Правила написания тестов

## Назначение

Документ фиксирует единый стиль unit, integration и architecture tests в проекте

Тест должен описывать поведение, а не внутренний способ реализации

---

## Именование тестов

Предпочтительный формат

```text
should_<expected_behavior>_when_<condition>
```

Если условие очевидно из поведения, допустим короткий формат

```text
should_<expected_behavior>
```

---

## Структура теста

Основной формат

```java
//given

//when

//then
```

Если действие и проверка неразделимы, например `assertThrows`, допустимо

```java
//when & then
```

Если создание объекта само является действием, допустимо

```java
//given & when
```

Формат `//given && when` не используется

---

## Что проверяет тест

Один тест должен проверять один сценарий поведения

Допустимо несколько assert, если они подтверждают один результат

Если проверяются разные причины, разные состояния или разные ветки поведения, нужно разделять тесты

---

## Типы тестов

### Model tests

Проверяют инварианты, immutability и accessor behavior

### Service tests

Проверяют observable behavior сервиса и ошибки на его границе

### Task / Operation tests

Проверяют orchestration, состояние context и преобразование ошибок в result

### Mapper tests

Проверяют contract mapping и значения по умолчанию

### Integration tests

Проверяют связку компонентов без проверки всех внутренних деталей

---

## Автоматическая проверка

На текущем этапе тестовый стиль сначала фиксируется как guideline

Автоматизировать стоит только те правила, которые уже стабилизировались и не создают шум при review

Минимальными кандидатами для будущей проверки являются

- Запрет `//given && when`
- Запрет test method names без префикса `should_`
- Поиск смешанных `GIVEN/WHEN/THEN` секций в одном тесте

Полная проверка структуры теста не вводится, пока стиль не будет применен вручную хотя бы к одному модулю
